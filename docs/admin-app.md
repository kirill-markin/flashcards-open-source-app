# Admin App

`apps/admin` is the server-protected admin SPA served from `https://admin.<domain>`.

Supported browser entrypoints:

- `http://localhost:3001`
- `https://admin.<domain>`

Each serves `/`, `/analytics`, `/analytics/general`, `/analytics/funnels` and `/analytics/audience`, and renders a not-found page on any other path. The route contract and its per-route loading are in [apps/admin/README.md](../apps/admin/README.md).

## Scope

The dashboard has three top-level analytics sections. `General` contains these three report sections, in page order:

- `daily-active-users`
- `catalog-deck-installs`
- `review-events-by-date`

`Funnels` is separate from General and stacks its funnels in one fixed order, top to bottom: mobile first launch, home page to web app, deck page to install, blog article to platform choice, blog article to web app. All five exist: `mobile-first-launch`, `home-to-web-app`, `catalog-installation` (the deck funnel), `blog-to-platform-choice` and `blog-to-web-app`; the order lives in the single [`funnelSections`](../apps/admin/src/reports/funnels/funnelSections.ts) list, whose comment also carries the rule that a funnel exists for one main user flow: a step is written as the designed path rather than as a union of every way it could be reached, so a rare bypass - a blog reader clicking a footer store badge without ever seeing the home page - is deliberately in no funnel rather than widened into one, and a flow that genuinely splits becomes its own funnel with its own first step, which is why the blog has two. Each funnel owns its query, parser, and display, reuses one step chart whose click-to-anchor step rides in the URL under its own parameter (`funnelFrom` for the deck funnel, `<funnelId>From` for the others: `mobileFrom`, `homeFrom`, `blogFrom` for the platform-choice funnel, which keeps the name shared links already carry, and `blogWebFrom` for the blog web-app funnel), and so can be added without changing General or introducing a generic reporting engine. The shared bar above them offers only the fields every funnel shares - date range, client platform, connection country and app interface language - and a field that belongs to one funnel sits in that funnel's own filter row, with the same URL parameter it has everywhere else. Each funnel also carries its own compact `Group by` field in its own filter row area under its heading, with its own dimension list and its own URL parameter `<funnelId>GroupBy`, omitted while it holds its `None` default; grouping one chart leaves the others alone. The field sits outside the chart because the chart is not drawn while a funnel loads or when nothing matches the filters, and a grouping has to stay clearable in both. Grouping is per person: the key is a property of the person over the selected dates, so the groups partition the funnel and sum back to it step by step unless that funnel's own row unit lets one person hold two keys, which is the deck funnel's case and is stated in its contract below, and every group is measured inside itself, from its own first step and from its own count at a selected step, so two groups of very different size compare as rates rather than as bar heights. A grouped chart draws the five largest groups, folds everything below them into one grey `Other`, and pins the people the dimension cannot place in their own `Unresolved` group, which is never folded and never takes one of the five. [`funnelGroupBy.ts`](../apps/admin/src/reports/funnels/funnelGroupBy.ts) owns the contract, the URL codec, the folding and the colours, [`FunnelGroupByPicker.tsx`](../apps/admin/src/reports/funnels/FunnelGroupByPicker.tsx) is the field. All five funnels declare their own dimensions beside the code that reduces them, four in a `query.ts` - the two blog funnels reusing the site-entry funnel's own list, since their cohort is keyed the same way, and adding the one dimension only they offer in [`blogFunnelEntry.ts`](../apps/admin/src/reports/blogFunnels/blogFunnelEntry.ts) - and the deck funnel, which reduces in the browser, in [`reportModel.ts`](../apps/admin/src/reports/catalogInstallFunnel/reportModel.ts), so every funnel shows the field.

Every funnel follows one rule, written beside the [`funnelSections`](../apps/admin/src/reports/funnels/funnelSections.ts) list: each step grows by at most one per person, and a person counts at a step only after reaching every earlier step. Each funnel counts entries from a fixed start date in its query, so no selection shows a partial first day: 2026-09-01 for mobile first launch ([`mobileFirstLaunchFunnelStartDate`](../apps/admin/src/reports/mobileFirstLaunchFunnel/query.ts)), 2026-09-23 for home page ([`siteEntryFunnelStartDate`](../apps/admin/src/reports/siteEntryFunnel/query.ts)) and deck page ([`catalogInstallFunnelStartDate`](../apps/admin/src/reports/catalogInstallFunnel/query.ts)), and 2026-09-24 for both blog funnels ([`blogFunnelStartDate`](../apps/admin/src/reports/blogFunnels/blogFunnelEntry.ts)), the first whole day after the blog's calls to action began leading to the home page partway through 2026-09-23. A range that starts earlier shows a note, and a range holding entries still inside their seven-day window shows a warning instead of cutting them.

One control above every funnel, [`FunnelAudienceModeControl`](../apps/admin/src/reports/funnels/FunnelAudienceModeControl.tsx), picks who they count. It is a single choice rather than a filter-bar field, it applies to every funnel at once so two funnels are always comparable, and it rides in the URL as `audience`, omitted while it holds its default. The three modes are declared in [`funnelAudienceModes`](../apps/admin/src/filters/analyticsFilters.ts) and expressed in SQL in [`funnelAudienceSql.ts`](../apps/admin/src/reports/funnels/funnelAudienceSql.ts):

- `with-anonymous-id` is the default and the behaviour every funnel had before the modes existed: a person is an `analytics.product_events_resolved.actor_id`, so a site visitor cookie, a mobile guest id or an account
- `signed-in` keeps only the actors that resolve to a real, non-guest account at any time up to now. The signal is a `auth.user_identities` row, a table whose own CHECK admits only `provider_type = 'cognito'` (`db/migrations/0031_guest_ai_identity_and_quota.sql`) and which `reporting_readonly` may read (`db/migrations/0066_reporting_readonly_operational_analytics.sql`). It covers both conversion shapes: a bound completion keeps the guest's user id and binds a Cognito subject to it, so the identity row is the only record that the guest became an account, while a merge or a web sign-in link rewrites `actor_id` to a target account that has one. A guest who never registered is out, one who registered later is in with their pre-registration steps, and somebody who has since deleted their account reads as not signed in, because the deletion cascades the identity row away
- `all` adds a second cohort of cookieless visitors, keyed on `analytics.product_events_resolved.daily_visitor_hash` plus the UTC day, one person per pair, counted only from [`funnelDailyVisitorHashStartDate`](../apps/admin/src/reports/funnels/funnelAudienceSql.ts). They are drawn as a lighter segment inside the bars, the shares are measured on the total, and the split is written above the bar and in the chart's hidden table. They can reach the site steps alone - a page view, then the web app link click, an install click on a deck whose page they viewed, or the home page view and platform click of the blog platform-choice funnel - because every step below reads a trusted in-app row that a cookieless browser never sends; their segment ending there is construction rather than drop-off. `blog-to-platform-choice` is the one funnel whose every step is such a site fact, so it is the only place this cohort is measured the whole way down. The mobile funnel has no such people at all, so `all` equals the default there, and `blog-to-web-app` does not read the cohort at all rather than adding it to its base, because its own first step is the click and cookieless clickers would raise the denominator of four steps they can never appear in

Filters reach the hashed cohort only where its rows can answer them: the platform is the row's own, compared exactly as its funnel compares the identified one - the bare column on the site-entry funnels, `COALESCE(..., 'unattributed')` on the deck funnel - and the site always reports web; the app interface language is the page view's own `ui_locale` rather than a person-level history; and a selected connection country removes the cohort altogether and says so, because those rows carry no country. When it is removed, the split columns, the chart's sub-heading, the lighter bar segment itself and the deck funnel's empty-state wording - the only one of the funnels whose empty state mentions the cohort - drop with it, so nothing on screen announces a segment the query did not read. The person key's day is `server_received_at`'s UTC day rather than `occurred_at`'s, because that is the day whose salt produced the hash; the skew-corrected `occurred_at` can name the neighbouring day around midnight and would split one browser's salt-day across two keys. The selected range bounds those scans on that same day rather than on `occurred_at`, so a person-day is whole or absent: a bound on `occurred_at` would let the range edge keep part of a day and drop the rest, and the site funnel reads the first page view as a `MIN` over what survives, so a clipped visitor's second page view would be read as their first. These rows have no actor, so the three actor-level arms of the one exclusion rule under [Backend surface](#backend-surface) cannot reach them, and neither can the deck funnel's rejection of the delisted `test` deck, which recognises the fixture by an app-side install start: a test account, an admin or an excluded actor browsing without consenting is counted among the hashed people, and so is the `test` deck's own cookieless traffic. Automated traffic is the one thing that does not reach them: [`0145_anonymous_client_automated_marker.sql`](../db/migrations/0145_anonymous_client_automated_marker.sql) added `analytics.product_events_resolved.automated_client`, which the collector stamps on exactly these rows, and [`funnelAudienceSql.ts`](../apps/admin/src/reports/funnels/funnelAudienceSql.ts) drops `automated_client IS TRUE` from every hashed page view and click, so a bot or a crawler that browses without consenting is not a hashed person at all. It is the only arm of the shared rule that can reach a row with no actor, and it keeps NULL, which is an unassessed row - one stored before the marker shipped - rather than a person, as that migration states. The exclusion-list, test-account and admin gaps above remain, and they are why `all` is not the default.

`all` is an upper bound on people rather than a count of them, and that is the one place the funnel rule does not survive the mode. A hash is written only where there is no identifier at all, so no *row* is in both cohorts, but the two can never be linked to each other, by design: the salt is unreadable and the `(hash, day)` pair is never resolved to a cookie id. Where the site must ask before it sets a cookie (the EEA and the UK), one human sends hashed page views before consenting and cookie-bearing ones after, so on that day they can be one hashed person and one identified person at the same step, and the two are added per step. No SQL can subtract that overlap; the funnel rule comment beside [`funnelSections`](../apps/admin/src/reports/funnels/funnelSections.ts) and the explainer of every section that shows the split state it, and it is the other reason `with-anonymous-id` is the default.

The audience mode is not a filter-bar field, so `Reset all` does not clear it: a reset returns the default range and every filter, and the funnels keep the audience they were reading. Removing the `audience` parameter from the URL, or picking `With anonymous ID`, is what returns it. For the same reason every funnel's empty state names the mode under `Signed-in only` ([`buildFunnelAudienceEmptyStateNote`](../apps/admin/src/filters/analyticsFilters.ts)): it is the only mode that removes people, and an empty funnel that blamed the filters alone would send a reader to clear fields that were never the reason.

`Audience` shows the distinct users who opened the app in range by observed connection country, actual event UI language, and platform, with upload country/language pairs and coverage. It shares every filter in General's bar, the one exclusion rule defined under [Backend surface](#backend-surface) and `daily-active-users`' rule that a credential-free `anonymous_client` row is not a person, and a per-user event threshold restricts its cohort rather than only the rows inside it, where the `Cards answered` threshold counts resolved review actors and every grade including `Again`. Its [query](../apps/admin/src/reports/audience/query.ts) and [display](../apps/admin/src/reports/audience/AudienceSection.tsx) define cohort and conservative sample matching; [Audience analytics](analytics-audience.md) defines collection and retention. Sparse samples cannot reconstruct daily presence or historical offline event geography.

The admin app is a separate React + TypeScript + Vite package. It does not reuse the web app runtime storage or sync code.

## Authentication and authorization

- Authentication source: the existing Cognito + `auth.<domain>` browser flow.
- Session transport: the existing cross-subdomain browser session cookies.
- Authorization source of truth: `auth.admin_users`.
- Admin grants are keyed by normalized email, not by app `user_id`.

Admin access is checked on every `/v1/admin/*` backend request:

- unauthenticated request: `401`
- signed-in non-admin: `403` with `ADMIN_ACCESS_REQUIRED`
- non-human transport such as `guest` or `api_key`: `403` with `ADMIN_HUMAN_AUTH_REQUIRED`

## Data model

`auth.admin_users` stores:

- `email`
- `granted_at`
- `granted_by`
- `revoked_at`
- `note`
- `source`

Active admin access means `revoked_at IS NULL`.

`auth.admin_users` is the runtime source of truth for active admin access.

`ADMIN_EMAILS` is only the local bootstrap input for local/manual deploy flows. For GitHub Actions deploys, the non-secret CI input is `CDK_ADMIN_EMAILS`, and `scripts/setup/setup-github.sh` creates it only if missing. After bootstrap, edit `CDK_ADMIN_EMAILS` manually in GitHub when changing the deployed bootstrap admin list. Migration/deploy paths:

- upsert active bootstrap grants for listed emails
- revoke removed bootstrap grants only when their current `source` is `bootstrap`
- leave `source='manual'` rows untouched

## Backend surface

The backend exposes:

- `GET /v1/admin/session`
- `POST /v1/admin/reports/query`

The query endpoint accepts:

- `sql`: raw SQL string executed by the backend through `reporting_readonly`

The query payload includes:

- `executedAtUtc`
- `resultSets[]`

Every charted surface and every filter option list drops the same people, through the single rule written in [`buildExcludedActorSqlLines`](../apps/admin/src/filters/filterSql.ts): an `@example.com` test account, anyone who has ever held an `auth.admin_users` row whether or not it was revoked, an actor listed in `analytics.excluded_actors` and not restored, meaning `restored_at IS NULL` (`db/migrations/0140_analytics_excluded_actors.sql` defines that list and its restore rules), and an actor any of whose rows the credential-free collector marked `automated_client IS TRUE` - a bot, crawler, headless browser or missing `User-Agent` ([`0145_anonymous_client_automated_marker.sql`](../db/migrations/0145_anonymous_client_automated_marker.sql)), read on the actor rather than the row so a smoke run that later signs into a real account is gone from every number, and never as `IS FALSE`, because NULL there is an unassessed row rather than a person. The rule is applied to every event of such a person that a charted number counts, and restated in the option lists so a value only an excluded person produced is never offered. The public `GET /v1/global/snapshot` applies all four arms to its own identity column ([global-metrics.md](global-metrics.md)), the automated one included, because a marked browser row resolves onto the account that later signed in. Every surface applies it on the row's own `actor_id`, the `catalog-installation` funnel included, because the shared visitor identity names somebody from the first deck page view; a visitor who never signed in resolves to their own browser id, which no account's address can name, so only the exclusion list and the automated verdict can reach such a row. Those two arms are not alike in one respect: `analytics.excluded_actors` carries `restored_at`, so a human can put a wrongly listed person back into every number, and the automated arm has no such path at all. `analytics.product_events` is append-only, so a stored verdict can never be rewritten, and a missing or empty `User-Agent` counts as automated, so one stripped-header request from a real person who later signs in removes that account from this dashboard and from the public snapshot permanently. That is the accepted cost of reading the verdict on the actor rather than on the row; undoing a particular case would take a new migration, not a dashboard change. Almost every catalog install in production history is an admin install, so `catalog-deck-installs` is nearly empty by design.

Attribution contract for `daily-active-users`:

- the section answers how many people were in the app on each calendar day, not how many answered a card; an active day is a day carrying that person's `app_opened` event
- identity works exactly as in `review-events-by-date`: grouped by `actor_id`, the same case-folded `org.user_settings` email join, the same one exclusion rule, and the same treatment of deleted accounts
- rows written by the credential-free collector, meaning `trust_level = 'anonymous_client'`, are dropped: no credential stands behind such a request and its `anonymous_id` is an unverified caller-supplied claim, so it is evidence that an event happened and not evidence that a person exists; that collector accepts `app_opened` like every other client-reportable name, so without the rule a signed-out marketing-site visitor would be a daily active user. `buildTrustedActorRowsFilterSql` owns the rule, and every other derivation that decides a person either applies it as well or cannot be reached by this collector at all; that helper's own comment carries the full list, says which of the two each entry is, and names the one derivation outside the admin package that restates the rule because it cannot import it; [Anonymous client analytics](anonymous-client-analytics.md) states the reading in full
- one row is one (UTC date, actor, platform), so a person active on the phone and the browser on one day is two rows and one active person; every unique-users number is a distinct count of actors and the platform chart is grouped, never stacked or summed
- `agent` stays its own visible series and is an upper bound on human agent use rather than a count of people, because a scheduled MCP client files an active day for its owner on every day it runs; `db/migrations/0121_backfill_synthetic_app_opened_days.sql` states this in full
- history from before the clients emitted the event is reconstructed from durable traces of somebody having been in a client, at roughly 85% coverage of the people who really opened the app on a sampled day, by that same migration and by its replays, the newest being `db/migrations/0126_backfill_app_opened_rollout_gap.sql`; replays keep running after the clients went live, so reconstructed rows also fall on days a client was already reporting
- reconstructed and live rows are deliberately not distinguished anywhere in the UI
- new versus returning is the actor's first trusted `app_opened` day over all history, trusted as the rule above defines it, which is this section's own cohort definition; `review-events-by-date` keeps using the first review day
- every field of the shared filter bar applies, all of them in SQL, so any filter change reloads the section

Attribution contract for `catalog-deck-installs`:

- the section answers how many catalog decks were installed on each calendar day and which decks those were; one install action by one person is one event, from `catalog_deck_installed`
- the event is server-emitted after the install transaction commits and keyed by `(workspace_id, install_id)`, so an idempotent replay of the same install cannot count twice
- everything the section needs is on the event, so no `catalog` or `sync` table is read; the deck dimension is `package_slug` and there are no deck titles or version numbers here
- identity works exactly as in `review-events-by-date`: grouped by `actor_id`, the same case-folded `org.user_settings` email join, and the same one exclusion rule
- one further exclusion is deliberate: the delisted test fixture, narrowly by `package_slug` `'test'` and never by package status, which would need a `catalog` grant this report does not take
- almost every install in production history is an admin install, so a nearly empty chart is the intended default rather than a defect; the `auth.admin_users` column grant the shared rule needs is `db/migrations/0125_reporting_readonly_admin_users.sql`, and without it deployed every section fails as HTTP 500 `INTERNAL_ERROR` rather than as a readable permission error
- platform is always `unattributed`: the producer writes NULL on purpose, because the install names no server-stored replica or guest session row and the request headers that do name a platform are a client claim, and `db/migrations/0120_backfill_product_analytics_server_facts.sql` wrote none either; the bucket is still derived with the same CASE as every other report, so picking any device platform empties this section
- new versus returning is the installer's first trusted `app_opened` day, which is `daily-active-users`' cohort definition rather than one of this section's own, rebuilt as a CTE over the same event so the two sections cannot disagree about which day a person was new on
- that CTE only covers installers with a trusted `app_opened` day inside the selected range, trusted as `buildTrustedActorRowsFilterSql` defines it, so an installer with no such day is in neither cohort and is kept only while both cohorts are selected, rather than being guessed into `new` or `returning`; an installer whose only in-range app opens came from the credential-free collector has no such day either and lands in that same no-cohort branch rather than flipping between `new` and `returning`
- every field of the shared filter bar applies, all of them in SQL, so any filter change reloads the section
- the placement, source, device-category and browser-language fields keep a person through a completed install attributed to one site click, here and on every other General and Audience section: the click resolves to the installer's own `actor_id` and precedes the install by at most the funnel's seven-day window, or, for rows written before the producers dropped it, shares the install's `install_journey_id`. [`buildCatalogInstallAttributionSql`](../apps/admin/src/filters/filterSql.ts) owns which click wins and the exclusions it applies, and the option lists read the same fragment
- the section carries one chart, installs per UTC day stacked by deck, plus summary tiles

Contract for the `mobile-first-launch` funnel:

- one row is one person whose first trusted event anywhere, over every event name and all of history, is an iOS or Android `app_opened` on a selected UTC day. The one exception is a `card_created` at most 60 seconds before that open, the [demo card](demo-card.md) seeded during first launch; any earlier `card_created` or other event keeps the person out; the later steps are the review screen, an answer reveal, a first `review_answered`, two reviews, reviews on two distinct UTC dates, and twenty reviews on three distinct UTC dates, each in order and within the deck funnel's seven-day window. First opens count only from the funnel's start date, the first UTC day on which iOS and Android had reported both the review-screen `screen_viewed` and `review_card_revealed`. [`query.ts`](../apps/admin/src/reports/mobileFirstLaunchFunnel/query.ts) owns the definitions
- the date range, the client platform (narrowed to iOS and Android, read off the first app open), the connection country and the app interface language all apply in SQL, the last two as on General; the one exclusion rule applies
- `Group by` offers three dimensions, each one key per person: `platform`, the first app open's own platform and so iOS or Android; `country`, the alphabetically first connection country that person's retained samples name in the range; and `language`, the alphabetically first app interface language their events in the range carry. The alphabetical rule is the rule rather than an approximation of a most-recent one, so a group key depends on the person and the range alone. The last two read the per-actor fragments in [`filterSql.ts`](../apps/admin/src/filters/filterSql.ts), which is the same evidence their filter fields read, and a person neither can place is grouped as `Unresolved`; [`query.ts`](../apps/admin/src/reports/mobileFirstLaunchFunnel/query.ts) declares all three. A group key is not narrowed by the filter of the same name: the country and language filters keep a person when any of their values in range matches the selection, while the group key is that person's alphabetically first value over the whole range, so a grouped chart can show a country or a language the filter above it did not select

Contract for the `home-to-web-app` funnel:

- one row is one person whose first marketing-site `site_page_viewed` carrying a visitor id is a `home` page on a selected UTC day, with no trusted event anywhere before it; the later steps are a `site_app_entry_clicked` with `target = 'web_app'`, a web `app_opened` sent as `authenticated_client` (opening the web app and signing in are one step, since signed-out web events are held until sign-in and the web app has no guests), a first `review_answered`, twenty reviews, and twenty reviews plus one on a later UTC day than the entry, each in order and within the deck funnel's seven-day window. The site facts are read only from `anonymous_client` collector rows and the in-app steps only from trusted rows. [`query.ts`](../apps/admin/src/reports/siteEntryFunnel/query.ts) owns the definitions and how the site and the app meet on one actor, and exports the cohort, the window, the web-app tail, the hashed-cohort lines and the group-key expression that the two blog funnels reuse, so the three differ only where they are meant to
- the site and the web app share the `analytics_visitor` cookie, and they join only when the web app's first analytics batch on a signed-in account links that cookie to the account, so no in-app step can be reached without a sign-in, and a pre-consent EEA or UK page view, which carries no visitor id, is in neither this funnel nor the blog ones
- the date range, the client platform (read off the entry page view, always web), the connection country and the app interface language all apply in SQL, the last two as on General; the one exclusion rule applies
- `Group by` offers one dimension, `Entry page language`: the `ui_locale` the entry page view itself carried, read back off the entrants' own entry rows inside the range rather than from a per-actor source joined beside the cohort, and deliberately not from the whole-history pass that finds those rows, where an ordered aggregate would cost that pass its hash aggregation on every load. A person enters on exactly one page view, so the key partitions the funnel and only an entry row that carried no locale at all is `Unresolved`. The cookieless visitors of `All` are keyed the same way off their own page view, so the lighter segment of the first two bars sits inside its own language group; both of that arm's counts are aggregates over its own cohort joined to its clicks rather than uncorrelated scalars, which at one row per key would attribute every cookieless entry and click to every group at once. Neither a person's connection country nor their app interface language is offered here, though the mobile and the deck funnels keep both: they read trusted rows only, and measured on production no entrant of this cohort has ever produced such a row - of the 201 actors that have sent a site page view, none has any trusted row - so every entrant falls in `Unresolved` under them today. That is the measurement and not a structural guarantee: the entry rule bars a trusted event only before the entry, so an entrant who signs in afterwards does have trusted rows in the range. The client platform is not offered, because the entry page view is always web. The dimension's id is `language`, the URL token shared links carry. A group is not the App interface language filter's answer, and the two cohorts differ in how: for a person with an identifier the field reads the locale of their trusted events in range, so narrowing it keeps only people who signed in while their key is the entry page's own locale, and for a cookieless visitor the same selection is applied through `buildHashedPageViewFilterSqlLines` to the entry page view itself, the row that arm is grouped by, so that segment can only appear inside the selected languages; [`query.ts`](../apps/admin/src/reports/siteEntryFunnel/query.ts) declares it, and both blog funnels offer it for exactly these reasons, beside the entry article that only they offer

Contract for the `blog-to-platform-choice` funnel, shown as "Blog article to platform choice":

- one row is one person whose first marketing-site `site_page_viewed` carrying a visitor id is a `blog_article` page on a selected UTC day, with no trusted event anywhere before it - the same cohort rule as the home funnel, on the other page kind. The two later steps are a `site_page_viewed` with `page_kind = 'home'` and then a `site_app_entry_clicked` with any `target`, each at or after the step above it and within the seven-day window the entry page view anchors. Every step is a site fact read from `anonymous_client` collector rows only. [`platformChoiceQuery.ts`](../apps/admin/src/reports/blogFunnels/platformChoiceQuery.ts) owns it
- the home page view is a step because it is the designed path: every call to action in an article leads to the localized home page and reports `site_internal_cta_clicked`, which this funnel does not read at all - the home page view that click produces is the step, so a released site bundle that stops reporting the CTA fact would not change these numbers. A reader who picks a platform without ever seeing the home page is outside this funnel by design rather than folded into a widened step
- the steps are joined on the visitor identity alone and never on `source`: the site classifies a page view's source from the page reported before it while a click on that same page classifies it from the document's own referrer, so after a client-side navigation the two rows legitimately disagree on it and a join including it would drop real conversions
- **the funnel ends at the platform choice on purpose, and there is no step below it, not even a cross-platform one.** A click on the App Store or Google Play badge leaves the browser, and no shared identity survives into the installed app, so what those people did next is unjoinable rather than unmeasured: state it as construction, never as drop-off. A step below the choice could therefore only ever resolve for the web app, which would be the same construction problem one level down; the web app's own activation is the `blog-to-web-app` funnel below, with that click as its own first step
- the cookieless `all` cohort reaches all three steps here, which no other funnel offers it: every step is a marketing-site fact a browser with no cookie reports exactly as an identified one does. This is the one place that cohort is a measurement of a whole flow rather than a segment that ends midway, and the section says so
- the section carries a per-target breakdown of the last step beside the bars: `web_app`, `app_store` and `google_play`, each person counted under the target of the very click that step counted, so the three lines partition the step and add up to it. A person whose only two clicks share an instant on different targets is resolved by `MIN` over the target, the same tie rule the entry locale uses, so the split is stable across runs. It is a card rather than three steps because the three are alternatives with no order between them, and it covers both cohorts, so the lines still sum to the step under `All`
- `target` is deliberately not a `Group by` dimension: the key is a property only a converter has, so every reader who never clicked would land in `Unresolved` and each real group would read 100% at the last step. The per-target breakdown answers the same question on the step where the target is a fact
- `Group by` offers the home funnel's `Entry page language` dimension and, only on the two blog funnels, `Entry article`: the entry page view's own `page_path` property, the route the site reports with its locale prefix already stripped, lowercase and with a leading and a trailing slash, so one post is one group across every language and this chart answers which posts pull people into the product while it measures the flow. It is keyed on the entry row exactly as the language is, not on a per-actor source, so it places the cookieless visitors of `All` too: their entry page view carries the path as an identified one does, while a dimension read from a person's history could say nothing about them. An entry row carrying no path at all, sent by a site bundle released before the property or on a route whose shape the site could not report, is `Unresolved`. Every article group came off a row the site reported as `blog_article`, since only such a page view admits an entry, but that is not a check that the article exists: the site classifies any `/blog/...` route that way, so a mistyped, deleted or badly linked article URL somebody really visited is drawn as its own small group rather than excluded - it is a real visit, and this repository holds no list of valid slugs to filter it against. The home funnel deliberately does not get the dimension, since its entry path is always `/`. The two ids are `language` and `article`, under this funnel's own `blogGroupBy` parameter, and its anchor rides in `blogFrom`; both parameter names are the ones shared links already carry, and [`blogFunnelEntry.ts`](../apps/admin/src/reports/blogFunnels/blogFunnelEntry.ts) declares the pair for both blog funnels

Contract for the `blog-to-web-app` funnel:

- the cohort is the same blog-article entrants, but **the first step is the web app link click, not the blog visit**, so every share below it is taken over people who did choose the web app and the tail reads as activation rather than as a mixture of activation and of readers who went to a store instead. A `site_page_viewed` with `page_kind = 'home'` between the two is deliberately not required: whichever page the reader clicked from, they are in this funnel with a full base under them. The steps below the click are the home funnel's tail unchanged in meaning - a web `app_opened` sent as `authenticated_client`, a first `review_answered`, twenty reviews, and twenty reviews plus one on a later UTC day than the entry - because both funnels build them from the same exported fragment. [`webAppQuery.ts`](../apps/admin/src/reports/blogFunnels/webAppQuery.ts) owns it
- the seven-day window stays anchored on the blog page view, exactly as the home funnel anchors it on its entry, so a reader who clicks late in that window has less of it left for the steps below; the maturing warning counts the clickers still inside theirs rather than every blog entrant, so it can never exceed the first step
- a group in which nobody clicked is not returned at all, for the same reason an empty group is dropped elsewhere: the click is the first step, so such a group would draw a band of zero bars and spend a legend entry on nobody
- the `all` audience counts exactly the people the default counts here, as it does on the mobile funnel and for the opposite reason: a cookieless visitor can produce the click and nothing below it, so the cohort is not read at all rather than inflating the base of four steps they can never appear in. Those people are measured in `blog-to-platform-choice` above
- the date range, the client platform (read off the blog page view, always web), the connection country and the app interface language all apply in SQL, the last two as on General; the one exclusion rule applies. `Group by` offers the same two dimensions as `blog-to-platform-choice` above, `Entry page language` and `Entry article`, both read off the blog article the person entered on, under this funnel's own `blogWebGroupBy` parameter, with its anchor in `blogWebFrom`. Neither places a cookieless visitor here, because this funnel does not read that cohort at all
- both blog funnels count entries from `blogFunnelStartDate`, one day later than the home funnel's own start date, because the blog's calls to action changed partway through 2026-09-23: comparing the blog family against the home funnel therefore needs a range that starts inside the later one, or the home funnel's first day is counted against a blog day that has no data

Attribution contract for the `catalog-installation` funnel, shown as "Deck page to install":

- every step counts people, not rows: a person adds at most one to each step, and only after reaching every earlier step, so step one, "Viewed any deck page", is a person who viewed the page of any deck, and the click and everything below it must be on a deck whose page that person viewed. `countPeopleAtEachStep` in [`reportModel.ts`](../apps/admin/src/reports/catalogInstallFunnel/reportModel.ts) owns the reduction
- one row is one visitor identity and one deck version, anchored at that identity's first `site_page_viewed` with `page_kind = 'catalog_package'` and that `package_version_id` whose `occurred_at` falls in the selected UTC dates, read only from `origin = 'client'` and `trust_level = 'anonymous_client'` rows; coming back to the same deck page is the same person arriving again and never a second row. Step two is the first `catalog_install_clicked` on the same deck version. There is no historical backfill and no Vercel aggregate is converted into visit history
- people count only from the funnel's start date, so a range before it shows a note rather than drop-off. Older, click-only history is deliberately not reachable here: the funnel starts at the page view
- every step and every exclusion is joined by `analytics.product_events_resolved.actor_id`. A row the browser sends with no account credential — the deck page view, the site click and the signed-out import screens — resolves through the shared `analytics_visitor` cookie, and onto the account once the web app records an `authenticated_client` identity link for that cookie; the signed-in app's rows carry the account already. That is what carries a person from the deck page view to the server install. The auth origin's rows are the exception, and the sign-in branch below states what that costs
- **only a click sent with the shared visitor cookie can reach the click step or any step below it**. A `catalog_install_clicked` body that claims no `anonymousId` is stored under its per-attempt `install_journey_id` (`readAnonymousId` in `apps/backend/src/productAnalytics/anonymousEvent.ts`), which nothing else shares, so it never meets the page view's identity. A page view before the visitor consents carries no visitor id and is not in the funnel at all
- selectable history reaches back to the first identified deck page view, which is folded into the shared picker's bounds as a union with the review-events range, so a range with data in only one area is still selectable
- later steps must occur in order with equal timestamps allowed and fall within seven days of the page view even when that follow-up is after the selected cohort's end date; where the event names a deck they must also keep the visit's `package_version_id`. Repeated milestones do not add another row
- the main path is viewed any deck page, install clicked, import screen, import confirm, install started, installed, then the three engagement steps — one review, twenty reviews, and twenty reviews plus a review on a later UTC day than the install. They are steps of the one funnel rather than a card beside it, nested so no step can exceed the one above it, and null together on a row with no server install rather than zero, so a missing install is not read as a drop-off inside engagement
- the import-screen, import-confirm, signed-out-gate and confirm-after-sign-in steps are `screen_viewed` rows, which carry no properties at all and therefore name no deck: a visitor who clicked two deck versions in range has those steps satisfied on both rows by the same view. Only the click, install start, install and failures require the row's own `package_version_id`
- import confirm is the `catalog_import_confirm` screen view and deliberately not `catalog_install_preview_ready`, which marks the same moment. The screen view is the account-side fact: the signed-in app reports it with the account's credential, so it meets the install with no identity link, while the preview fact goes out on the credential-free collector and reaches the account only through the web app's link for its visitor cookie. The `catalog` screen behind the import-screen step is a general catalog-browse surface that only the web import route emits today; `query.ts` says what a future browse screen would do to it
- the sign-in branch is the signed-out import gate, signed in on this browser, and the import confirm after it. Signed in on this browser is the first `screen_viewed` after the gate that the same browser, meaning the same `anonymous_id` as the gate row, sent with an account credential (`trust_level = 'authenticated_client'`); it names no deck, so it is that person's sign-in rather than this deck's. The browser equality is what keeps a person who already had an account from counting when they give up at the gate and use the app on another device, where their rows share the actor but not the cookie. It is deliberately not the auth origin's `signin_succeeded`: the auth origin posts on a guest credential whose `user_id` outranks the visitor cookie in `analytics.product_events_resolved`, and those rows reach the account only through the `server_derived` guest-upgrade link written inside a 150 ms budget that a first-ever sign-in usually overruns, so keyed on it the step would miss most of the people the gate is shown to. The auth origin's sign-in screen view and `signin_code_requested` are not steps for the same reason: a person who abandons there stays on a guest id the cohort never contains, so those steps could only count people who went on to succeed. Gate to signed in is the whole drop-off this branch can show. The retired `catalog_install_*` landing and sign-in names are not read at all
- only an `origin = 'server'` `catalog_deck_installed` is success, while `catalog_deck_install_started` remains intent
- every filter applies in SQL. The date range, the client platform (always web on a site row) and the installed deck read the anchoring page view. The connection country and the app interface language keep an identity as on General, from its trusted events in the selected dates. The placement, source, device category and browser language describe the install click, so they narrow which click counts as step two, and so everything below it, and never the deck page views above it: a narrowed selection reads as a lower click rate rather than a smaller top. The four click dimensions take their option lists from those clicks directly on this area, not through the completed-install bridge General and Audience read, because a click here never had to become an install. The lists cover every day rather than the selected ones, so a value outside the range is still offered, and picking it zeroes the install-click step and everything below it while the deck page views stay
- `Group by` offers seven dimensions, all of them values the visit row already carries: `deck` (the package behind the row's deck version, keyed on that package and labelled with the deck's public slug, so two versions of one deck are one group and a visit whose package the catalog no longer holds is `Unresolved`), `country` and `language` (the identity's, read from the same per-actor fragments in [`filterSql.ts`](../apps/admin/src/filters/filterSql.ts) the two filter fields read), `placement` and `click-language` (the row's own install click's, so a person who never clicked is `Unresolved` under them), and `source` and `device-category` (the row's own deck page view's, so every row carries one). The reduction is the browser's rather than SQL's, because the query already returns one row per visit: a dimension is a reader over a row and a pick regroups the rows in hand without reloading. Both per-actor sources are joined on every load for that reason, each bounded to the funnel's own cohort, a bound the planner applies after the scan rather than under it, so their cost still follows the selected range; [`query.ts`](../apps/admin/src/reports/catalogInstallFunnel/query.ts) carries the measurement, and reaches the deck's package and slug through `catalog.package_versions` and `catalog.packages`, whose two columns each are the whole of the reporting grant in [`0148_reporting_readonly_catalog_deck_names.sql`](../db/migrations/0148_reporting_readonly_catalog_deck_names.sql). [`reportModel.ts`](../apps/admin/src/reports/catalogInstallFunnel/reportModel.ts) declares all seven and runs `countPeopleAtEachStep` once per group. **Only `country` and `language` partition the people.** The row unit is one identity and one deck version, so under the other five a person whose deck rows disagree on the key is in two groups and the bars add up to more people than the funnel holds: two different decks under `deck`, while two versions of one deck merge into one group; a browse that arrives by `search` on one deck and `internal` on the next under `source` and `device-category`; and a click on one deck but not another under `placement` and `click-language`, which puts the same person in a value group and in `Unresolved` at once. `Other` is therefore re-counted from the underlying rows rather than summed from the groups it folds, and stays distinct people. No dimension is narrowed by the filter field of its name: the country and the language are the identity's over the range, and the other five are the row's own while those four filter fields read the install click, which may be a later session than the page view the row is anchored at, so a grouped chart can show a value the filter above it did not select. The cookieless visitors of the `all` audience carry no identity and no attributed click, so with any dimension selected they are all in `Unresolved` and their lighter bar segment is there alone. `click_placement` is parsed as free text rather than against the three declared placements, because it is only ever a group key: a fourth placement should become its own bar instead of failing the report's four result sets. Nothing else in the section is grouped: the sign-in branch, the failure totals, the median, the two no-visit lines and the maturing warning stay funnel-wide
- failure totals count distinct people per observed stage/reason, so they are not inferred abandonments and are not mutually exclusive; the report separately shows, as distinct people, those with an import preview or a server install and no page view of that deck in the selected dates, those whose first deck page view is still inside its seven-day window, and installers split by whether they were first seen at the deck page view of their first install
- a row whose `actor_id` resolves to NULL is excluded everywhere. That is a browser that refused consent and was given no identifier at all: it is an event belonging to no identity rather than an event missing one, and without that exclusion the whole identity-free remainder would collapse into one phantom visitor that no filter and no exclusion could reject
- new means the installing identity produced no trusted row at all before the deck page view, over every event name and read over that identity's whole history, trusted as `buildTrustedActorRowsFilterSql` defines and states it. The shared identity made that predicate matter more rather than less: the anchoring page view is itself a credential-free row resolving onto the same identity, so without the trust rule every installer would have an event at their own first visit and none would ever read as new
- the delisted `test` deck is excluded when an install-start fact by the same identity and deck version identifies it; the one exclusion rule applies on the row's own `actor_id`, with no bridge to an install, so it reaches a person backwards over every row of theirs this report reads, including the ones sent before they signed in
- the two no-visit lines can be narrowed by the date range, the installed deck, the client platform, the connection country and the app interface language, but by none of the click dimensions, which a row with no click carries none of. A deck page view before the first selected day counts as no visit on both, exactly as the funnel treats it. Each is a lower bound on what the funnel cannot hold rather than the whole of it: a person whose click was dropped by a placement, source, device-category or browser-language selection, or whose step chain is broken, is equally unheld and counted by neither. A server install carries no platform, so selecting any device platform empties its line

The events this reads are in [catalog-install-funnel.md](catalog-install-funnel.md).

Current v1 attribution contract for `review-events-by-date`:

- the report is intended for the current single-effective-learner workspace model
- every chart reads `analytics.product_events_resolved` and no other product table; the relations it always touches are the three the one exclusion rule reads besides that view itself, `org.user_settings` joined from `actor_id`, `auth.admin_users` and `analytics.excluded_actors`, the rule's automated-client arm re-reading the event view for the actors marked there; the shared filter bar puts one more into that SQL on demand, `analytics.installation_country_observations` inside a country selection

- the old dashboard showed nothing for them, but not because of its replica join: the same deletion drops the person's sole-member `org.workspaces` rows and `content.review_events` cascades with them, so the rows that query read were already gone
- an account deleted before it had any analytics history is absent here entirely: there was nothing to anonymize, and the `0120` backfill keeps only reviews whose author still has an `org.user_settings` row, which that deletion removed; do not reconcile a total here against `content.review_events` expecting those reviews, in either table
- the `org.user_settings` join folds the stored side with `pg_catalog.lower`, because `actor_id` is a UUID rendered as canonical lowercase hex while `org.user_settings.user_id` is an unconstrained `TEXT` primary key; comparing as stored would miss an uppercase-hex row and count a test account instead of excluding it
- the default chart range is shared by every section and covers the last 30 days ending today, inclusive, in the report timezone; the picker can narrow it or widen it back over the full history, which starts on the first calendar day carrying an `app_opened`, `review_answered`, `friend_invitation_created`, or `friendship_created` event
- the fields of the shared filter bar, which [the filter model](../apps/admin/src/filters/analyticsFilters.ts) declares and explains one by one, are all applied in SQL and reach every chart, including the community charts, where a cohort or platform filter keeps community rows only for users that still have review events in range, and the user filter list also offers users with community activity but no review events in range; Reset all returns date range to the same last-30-days default and clears every other filter; the whole selection is carried in the query string, so a reload or a shared link reopens the same filtered view
- platform is read off the event row and never derived; the buckets are `web` / `android` / `ios` / `agent` / `unattributed` and are always split, never summed, so agent-API activity cannot read as a person on the site; `agent` is an upper bound on human agent use rather than a count of people, because a scheduled or polling machine client files activity on a timer, and `db/migrations/0121_backfill_synthetic_app_opened_days.sql` states this in full
- a `review_answered` row carries the platform the backend resolved from the replica that recorded the review, and migration `0122` filled the same value on the reconstructed history, `0123` on the live rows the producer wrote before it could resolve one; a device value appears for a `client_installation` replica on `ios`, `android`, or `web`, and for an AI-chat review whose chat run was started by a request that named its device (`apps/backend/src/productAnalytics/serverFacts/reviewAnswers.ts`); a machine-API replica resolves to `agent`, while any other AI-chat review and a seed/reset replica leave the column NULL, as does a review whose replica row is gone
- `unattributed` therefore means the row carries no resolved device fact, either because the actor behind it is not a device or because no device could be resolved for it, and not either case alone; it stays its own bucket rather than being guessed at or summed into a device
- a bulk review-history import ensures a replica from the importing request and stores it on every imported review event, so one import files its whole batch under the device that performed the import rather than under the device that originally answered; those rows also land on the import day, because `occurred_at` falls back to the server anchor outside the 30-day window, so a large import shows as a single-platform spike on a single day rather than as a defect
- review dates are `occurred_at`, the client clock kept only inside a 30-day window ending at a server anchor and replaced by that anchor outside the window in either direction; inside the window a day is when the person answered rather than when the answer synced, and a first review day can therefore move earlier than the old dashboard reported it
- outside that window the day is the anchor's, and on the review history import the anchor is that request's own clock, so an offline, imported, or guest-merged history older than 30 days lands on sync day rather than on the days it was answered
- friend invite charts count `friend_invitation_created` per actor per UTC date and stack those counts with the same per-user colors as the review-events chart
- friend connection charts are a running sum of `friendship_created` per actor through the end of each UTC date; the producer emits one event per directed friendship row, so the all-user column is intentionally twice the number of friendship pairs
- that running sum is exact given the events, not against `community.friendships`: the emission is best effort and swallows its own failure, and because the chart is cumulative one dropped write lowers that actor's count on that day and on every day after it permanently, with no repair path; a swallowed emission is the first thing to check when the panel disagrees with `community.friendships`, and a duplicate pair is the second, where `community.friendships` holds more than one row for the same invitation and viewer, those rows derive one `event_id`, and `ON CONFLICT DO NOTHING` collapses them into a single event that `0120` accepts as an undercount and reports through a `RAISE NOTICE`
- a `friendship_created` event names only its own viewer, so a friendship whose other side is an `@example.com` test account is no longer excluded
- do not interpret this report as durable review authorship: `content.review_events.reviewed_by_user_id` is `ON DELETE SET NULL`, and account-deletion anonymization rewrites `analytics.product_events.user_id`, so an actor here is who the events currently resolve to rather than a permanent author record

Attribution contract for `card_created` and `deck_created`, which no admin report charts; these rows exist only in `analytics.product_events`, and this is for reading them there:

## Reporting data path

Deployed admin analytics do not query Postgres from the browser.

The path is:

1. browser requests `api.<domain>/v1/admin/...`
2. backend Lambda authenticates the human admin session
3. backend Lambda opens the dedicated reporting pool with `reporting_readonly` and a conservative process-local connection cap
4. admin SPA sends chart-owned SQL to `POST /v1/admin/reports/query`
5. backend Lambda runs the read-only SQL inside the VPC against private RDS and returns tabular JSON result sets

`reporting_readonly` remains read-only and supported in two modes:

- manual/operator analytics through an SSM tunnel
- controlled server-side admin analytics from the backend Lambda

## Local development

Install and run:

```bash
npm install --prefix apps/admin
make db-up
make auth-dev
make backend-dev
make admin-dev
```

Reserved local ports:

- web: `http://localhost:3000`
- admin: `http://localhost:3001`
- backend: `http://localhost:8080`
- auth: `http://localhost:8081`

Local allowlists must include both localhost origins for auth redirects and backend CORS.

When the backend runs with `AUTH_MODE=none` and `ALLOW_INSECURE_LOCAL_AUTH=true`, `/v1/admin/*` accepts localhost-only admin requests and attributes them as `local-admin@localhost`. That insecure shortcut is limited to loopback hosts and is not supported on deployed domains.

## Self-hosted deploy

For the first `admin.<domain>` rollout, use this exact order:

1. Set `ADMIN_EMAILS` in root `.env` for the initial bootstrap.
2. Run `bash scripts/cloudflare/setup-admin-domain.sh --domain <domain>` when the admin certificate does not exist yet.
3. Run `bash scripts/setup/setup-github.sh` so GitHub Actions picks up the admin certificate ARN and the initial bootstrap admin list.
4. Deploy normally.
5. Run `bash scripts/cloudflare/setup-dns.sh --stack-name <stack-name> --domain <domain>` after the stack exposes `AdminCustomDomainTarget`.
6. Run `bash scripts/checks/check-public-endpoints.sh --stack-name <stack-name>` after the DNS change.
7. Open `https://admin.<domain>`.
8. Sign in with the existing Cognito email.
9. Confirm that `https://admin.<domain>/analytics/general` loads.

Important rollout note: if `CDK_ADMIN_CERTIFICATE_ARN_US_EAST_1` or `CDK_ADMIN_EMAILS` was added to GitHub after a release workflow had already started, that in-flight workflow does not see the new values. In that case, finish the setup above and then run another deploy or rerun the workflow.

If the environment already exists and the deployed bootstrap admin list changes later, update `CDK_ADMIN_EMAILS` manually in GitHub before deploying.

The supported browser entrypoint is `https://admin.<domain>`.
The admin frontend fails fast on any other non-local hostname. Do not serve the browser entry on a raw CloudFront or other non-admin hostname, and do not treat the raw CloudFront distribution hostname as a supported admin URL.
