# Store Analytics Import

[A scheduled Lambda](../infra/aws/lib/scheduled-jobs/store-analytics-import.ts) copies store reports into the `store_analytics` schema ([migration](../db/migrations/0181_store_analytics_schema.sql)). It runs hourly at minute 20 UTC as the IAM role `FlashcardsStoreReportsImportRole`; [the handler](../apps/backend/src/entrypoints/scheduledJobs/lambda-store-analytics-import.ts) runs App Store reports, Google Play reports, then Google native billing history under one lock and one 12-minute budget. One source failing does not stop the other; the run still fails, and each failure is reported to Sentry. The importers log one `store_analytics_apple_import_completed` and one `store_analytics_play_import_completed` record per run.

## App Store

- Source: every instance (daily, weekly, monthly) of every report in every App Store Connect Analytics report request for the app, read with the team key in Secrets Manager `flashcards-open-source-app/app-store-connect-reports`. The key can only read; requests are created as described in [App Store Analytics Access](app-store-analytics.md).
- Tables: [the report mapping](../apps/backend/src/storeAnalytics/appleReports.ts) routes each report family to its table and every other report to `apple_other_report_rows`. Columns are matched by header name.
- Replacement: [the importer](../apps/backend/src/storeAnalytics/appleImport.ts) keeps, per report name, granularity, detail level and report date, only the rows of the newest processing date. An equal processing date replaces the earlier copy, so the ongoing and snapshot requests never double a date.
- Retries: a failed instance is reported to Sentry and retried by the next run. A run stops starting instances after 12 minutes and the next run continues. Runs are serialized by a session advisory lock: a run that cannot take it within 10 seconds fails and alerts like any other failed run. The run fails while no `ONGOING` request is active; an App Store Connect Admin must then create one.

## Google Play

- Source: every CSV under `stats/` and `financial-stats/subscriptions/` in the Play Console reports bucket `pubsite_prod_6698442103294061634`, for every package in it. Every `sales/salesreport_YYYYMM.zip` is also enumerated, with all CSV entries decoded; only Nibomo package rows and allowlisted financial columns are retained. `reviews/` and `earnings/` are not imported. [The client](../apps/backend/src/storeAnalytics/googleStorageClient.ts) has no key file: the Lambda role federates through Workload Identity provider `aws-store-reports-import` in pool `nibomo-aws-store-reports` and impersonates `nibomo-store-reports@flashcards-open-source-app.iam.gserviceaccount.com`, a Play Console user allowed to download bulk reports and view financial data. The provider trusts only `FlashcardsStoreReportsImportRole`; the billing identity in [Google Play subscriptions](google-play-subscriptions.md) is separate.
- Financial orders: [the native collector](../apps/backend/src/billing/history/googleImport.ts) uses the same reports-role federation and service account with Android Publisher scope. [Backfill, source coverage and permissions](billing-history.md#google-backfill-and-verification) own its operational procedure.
- Tables: [the file mapping](../apps/backend/src/storeAnalytics/playReports.ts) routes each file by directory and file-name breakdown, and every other file, including a breakdown the schema does not list, to `play_other_report_rows`. Columns are matched by header name; the byte order mark picks UTF-16LE, UTF-16BE or UTF-8. [Sales decoding](../apps/backend/src/storeAnalytics/googleSalesReports.ts) writes financial rows to `play_other_report_rows` with `report_name = sales`; it drops buyer addresses, device details, titles, free text and unknown columns before insertion. Those rows discover orders and reconcile native charges; they are not additional payments.
- Replacement: Google rewrites a month's file in place as a new object generation. [The importer](../apps/backend/src/storeAnalytics/playImport.ts) records `<objectName>#<generation>` as `source_ref` and, in one transaction, deletes every earlier generation of the object with its rows before inserting the new one.
- Retries: a failed file, including one in an unknown encoding or with an unknown breakdown header, is reported to Sentry and retried by the next run. The report summary exposes `salesInventoryComplete` independently of statistics CSV results and survives file failures. Native history collection still runs after report errors; its [coverage contract](billing-history.md#google-backfill-and-verification) requires complete sales inventory for order coverage. Report errors still fail the shared invocation.

## Freshness

`store_analytics.import_files` has one row per imported App Store segment or Play file. For App Store, read the latest `processing_date` and `imported_at` per `report_name` and `granularity` there; an instance absent from it has not been imported. Apple deletes instances 35 days after generation. For Google Play, read `file_month`, `report_date_to` and `imported_at` per `report_name`; Google posts each day 3–7 days late.
