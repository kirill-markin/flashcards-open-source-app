# Publish a public flashcard deck

## Reference

Before drafting, inspect one published deck. The complete public JSON snapshot is `GET https://api.flashcards-open-source-app.com/v1/catalog`; do not download it only for reference. Read one deck and at most five of its cards through bounded endpoints:

```sh
package_json="$(curl --fail --silent --show-error 'https://api.flashcards-open-source-app.com/v1/catalog/packages?limit=1')"
printf '%s\n' "$package_json" | jq '.catalogPackages[0]'
package_version_id="$(printf '%s\n' "$package_json" | jq -r '.catalogPackages[0].latestVersion.packageVersionId')"
curl --fail --silent --show-error "https://api.flashcards-open-source-app.com/v1/catalog/package-versions/${package_version_id}/cards?limit=5" | jq '.cards'
```

1. Read `AGENTS.md`, `apps/backend/src/catalog/authoring/`, `apps/backend/src/routes/catalog/admin.ts`, `apps/backend/src/routes/catalog/adminImageIngestion.ts`, and `apps/backend/src/routes/catalog/install.ts`, plus the sibling website's `src/lib/publicCatalogBuild.ts` and `.github/workflows/daily-vercel-rebuild.yml`. Use the current code as the API contract.
2. Agree on the topic, card source and order, author, stable slug, title, summary, Markdown description, language and topic tags, license, content warning, and desired cover. For a deck that tracks the latest release, keep one durable canonical slug, put source and release years in versioned metadata, and create another slug only when distinct versions must remain independently installable. By default, put one short, recognizable, uncommon deck-specific tag on every card. Accept the small collision risk instead of adding a namespace or prefix; avoid generic tags such as `study`, `cards`, or `deck`. Do not add section, status, difficulty, or maintenance tags unless the user explicitly requests them. Review all public text and media with the user before state-changing API calls.
3. Prefer a Git-ignored `tmp/public-catalog/<slug>/` review bundle. Reuse the portable workspace package layout for `cards.json` and optional card files under `media/`; add `catalog.json` for catalog-only metadata, an optional `cover.png`, `cover.jpg`, or `cover.webp`, and a generated `review.md`. Only `cards.json` and referenced `media/**` entries belong in a workspace import ZIP; exclude the catalog-only and review files. This bundle is recommended, not required. Covers and card images are optional and may be created with an available LLM image-generation tool; review generated media, alt text, credits, and licenses before upload. Before choosing a cover aspect ratio, inspect the rendered catalog crops and the SEO metadata wiring. When one image must serve catalog and search or social previews, prefer a relevant, text-light, center-safe 16:9 image at least 1200 pixels wide and review every crop; do not assume the package cover feeds Open Graph, Twitter, or JSON-LD metadata.
4. Finalize public-only cards in the reviewed bundle. Use a source workspace and the agent API when the cards already belong in an account; upload its JPEG, PNG, or WebP card images through the workspace media endpoints and reference ready assets with `fcasset:` links. The workspace snapshot flow copies those images into the catalog version automatically.
5. Before any catalog state change, manually read every final card front and back from the actual deck data. Scripts may check mechanical properties such as count and order, but must not replace this content review. For strict-answer decks, compare every question and accepted answer directly with the authoritative source, including qualifiers, alternatives, caveats, and changing or location-dependent answers. For open-ended decks, judge each prompt and answer individually for correctness, relevance, clarity, internal consistency, and whether the answer makes sense and addresses the prompt; verify factual claims against authoritative sources when available. Report and resolve every finding before publication.
6. Load `FLASHCARDS_OPEN_SOURCE_API_KEY` from the Default Checkout's untracked `.env`; never print or commit it. Prefer the `/v1/admin/catalog` endpoints with `Authorization: ApiKey $FLASHCARDS_OPEN_SOURCE_API_KEY`; the key owner's profile email must have an active `auth.admin_users` grant. A signed-in browser session remains supported as an alternative and requires CSRF protection for state-changing requests. Create or update the author and package draft. For a cover, append each non-null reviewed `altText`, `credit`, and `license` value to `URLSearchParams`, then upload the raw bytes with the image `Content-Type` to `PUT /v1/admin/catalog/packages/{packageId}/cover?${params.toString()}`; it normalizes and attaches the image as `cover`. Keep those reviewed values with the cover throughout publication; do not replace them with title or description fallbacks. Upload direct card images with `POST /v1/admin/catalog/packages/{packageId}/media-assets/images` and `x-package-media-key`. Save every created author, package, media, and version ID in the review bundle.
7. Treat card order as a learning contract. For a reviewed bundle, call `POST /v1/admin/catalog/packages/{packageId}/versions` with explicit unique ordinals `1..N`. For a workspace snapshot, pass `cardIds` to `POST /v1/admin/catalog/packages/{packageId}/versions/from-workspace` in the exact intended sequence. Move the immutable version through `draft -> submitted -> approved`, then publish it with the review-status and publish endpoints. After an ambiguous `5xx`, reload the existing package draft or public status and reuse known IDs and the same payload only when safe; never create replacement resources automatically. Publish only when the user has explicitly authorized making the deck public; corrections after publication require a new version.
8. Verify through `GET /v1/catalog` that every published ordinal, text, tag, and media reference matches the review bundle. Install the version into an empty verification workspace, use `addImportTag: false` when every source card already has the deck-specific tag, and compare every installed front, back, and tag in `created_at ASC` order; the current backend maps ordinals to strictly increasing creation timestamps. Rebuild the sibling static website through its existing deployment workflow, wait for the Vercel deployment itself to reach `Ready` rather than treating the deploy-hook workflow as completion, then check the live HTML and Markdown pages, canonical URL, metadata and JSON-LD, sitemap entry, actual cover crops, media rendering, and install link. Report the public URL and package version ID.
