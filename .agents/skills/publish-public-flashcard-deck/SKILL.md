# Publish a public flashcard deck

1. Read `AGENTS.md`, the catalog authoring code under `apps/backend/src/catalog/authoring/`, the admin routes in `apps/backend/src/routes/catalog/admin.ts` and `apps/backend/src/routes/catalog/adminImageIngestion.ts`, and the sibling website's `src/lib/publicCatalogBuild.ts`. Use the current code as the API contract.
2. Agree on the topic, source workspace, ordered cards, author, stable slug, title, summary, Markdown description, language and topic tags, license, content warning, and desired cover. For a deck that tracks the latest release, keep one durable canonical slug, put source and release years in versioned metadata, and create another slug only when distinct versions must remain independently installable. By default, put one short, recognizable, uncommon deck-specific tag on every card. Accept the small collision risk instead of adding a namespace or prefix; avoid generic tags such as `study`, `cards`, or `deck`. Do not add section, status, difficulty, or maintenance tags unless the user explicitly requests them. Review all public text and media with the user before state-changing API calls.
3. Prefer a Git-ignored `tmp/public-catalog/<slug>/` review bundle. Reuse the portable workspace package layout for `cards.json` and optional card files under `media/`; add `catalog.json` for catalog-only metadata, an optional `cover.png`, `cover.jpg`, or `cover.webp`, and a generated `review.md`. Only `cards.json` and referenced `media/**` entries belong in a workspace import ZIP; exclude the catalog-only and review files. This bundle is recommended, not required. Covers and card images are optional and may be created with an available LLM image-generation tool; review generated media, alt text, credits, and licenses before upload. Before choosing a cover aspect ratio, inspect the rendered catalog crops and the SEO metadata wiring. When one image must serve catalog and search or social previews, prefer a relevant, text-light, center-safe 16:9 image at least 1200 pixels wide and review every crop; do not assume the package cover feeds Open Graph, Twitter, or JSON-LD metadata.
4. Create or finalize the cards in the source workspace through the agent API. For card images, upload JPEG, PNG, or WebP files through the workspace media endpoints and reference the ready assets with `fcasset:` links. The workspace snapshot flow copies those images into the catalog version automatically.
5. Before any catalog state change, manually read every final card front and back from the actual deck data. Scripts may check mechanical properties such as count and order, but must not replace this content review. For strict-answer decks, compare every question and accepted answer directly with the authoritative source, including qualifiers, alternatives, caveats, and changing or location-dependent answers. For open-ended decks, judge each prompt and answer individually for correctness, relevance, clarity, internal consistency, and whether the answer makes sense and addresses the prompt; verify factual claims against authoritative sources when available. Report and resolve every finding before publication.
6. Prefer calling the `/v1/admin/catalog` endpoints headlessly with `Authorization: ApiKey fca_…`; the key owner's profile email must have an active `auth.admin_users` grant. A signed-in browser session remains supported as an alternative and requires CSRF protection for state-changing requests. Create or update the author and package draft. For a cover, append each non-null reviewed `altText`, `credit`, and `license` value to `URLSearchParams`, then send the raw image bytes to `PUT /v1/admin/catalog/packages/{packageId}/cover?${params.toString()}` with the image `Content-Type`. Keep those reviewed values with the cover throughout publication; do not replace them with title or description fallbacks.
7. Treat card order as a learning contract: pass `cardIds` to `POST /v1/admin/catalog/packages/{packageId}/versions/from-workspace` in the exact intended study sequence so the backend assigns and preserves matching ordinals. Verify stored ordinals, public preview order, and the first cards in the installed review flow; request-array order alone does not prove user-visible study order. When every source card already has the deck-specific tag, verify installation with `addImportTag: false` so the optional import tag does not create a redundant second tag. Move the immutable version through `draft -> submitted -> approved`, then publish it with the review-status and publish endpoints. Publish only when the user has explicitly authorized making the deck public; corrections after publication require a new version.
8. Verify the published package through `GET /v1/catalog`, rebuild or redeploy the static website so it fetches the new catalog dump, then check the public HTML and Markdown pages, canonical URL, metadata and JSON-LD, sitemap entry, actual cover crops, media rendering, and install flow. Report the public URL and package version ID.
