# Publish a public flashcard deck

## Reference

Before drafting, inspect one published deck. `GET https://api.flashcards-open-source-app.com/v1/catalog` now redirects to an immutable CDN artifact holding the complete public JSON snapshot, so a plain `curl` needs `-L` to follow it; do not use that endpoint for reference and do not use it for per-deck verification. The only sanctioned read of that snapshot is the one step 8 names. Read one deck and at most five of its cards through bounded endpoints:

```sh
package_json="$(curl --fail --silent --show-error 'https://api.flashcards-open-source-app.com/v1/catalog/packages?limit=1')"
printf '%s\n' "$package_json" | jq '.catalogPackages[0]'
package_version_id="$(printf '%s\n' "$package_json" | jq -r '.catalogPackages[0].latestVersion.packageVersionId')"
curl --fail --silent --show-error "https://api.flashcards-open-source-app.com/v1/catalog/package-versions/${package_version_id}/cards?limit=5" | jq '.cards'
```

## Product defaults

- For a standardized full-course deck, do not block on the learner's current topic or school textbook. Confirm the curriculum edition, level, language, and exam session only when they change scope, then build a complete internal coverage ledger.
- Optimize title, slug, and description strongly for the exact learner query while remaining accurate, useful, and rights-safe. Put the primary course or exam query first when it accurately identifies the content. Verify applicable naming and trademark rules before using a third party's course, exam, or standard name; never use its logo or trade dress or imply official status, affiliation, or endorsement. Keep the public title and canonical slug evergreen for a stable curriculum; use the current year only in separate SEO metadata or a visible `Reviewed for <year>` line after an annual compatibility check. Preserve one package and URL across compatible years.
- For an independently authored common-knowledge deck intended for unrestricted reuse, default the license field to `Common knowledge · CC0 1.0` and keep it label-only. Apply CC0 to original questions, answers, organization, metadata, and original or LLM-generated media to the extent applicable rights exist. Put scope, provenance, and non-affiliation language in the description. Do not claim ownership of facts or license rights the publisher does not hold.
- When a course or examination owner is named, end the description with an independent, unofficial, non-affiliation notice; state that no examination questions, mark schemes, or curriculum text were copied when true; and link the owner's official requirements page. Keep these statements outside the license field.
- Default to no third-party media. Create original or LLM-generated visuals from facts with an independent composition; do not trace or redraw a specific source image. Use third-party media only when the user explicitly requests it and its provenance, license, attribution, and intended reuse are verified.
- Public catalog cards support optional images and LaTeX math; use either only when it materially improves the content. Write `$...$` inline for a short expression inside a sentence, with no space just inside either `$` and no digit right after the closing `$`; write a standalone display formula as its own block, with `$$` alone on the opening and closing lines and a blank line before and after it or the start or end of the card side, because a `$$` block that does not stand alone stays literal. Escape a currency `$` as `\$` (`\\$` inside JSON such as `cards.json`). Put math only in a plain paragraph that holds no link, image, bold, italic, strikethrough, or code anywhere in it, and keep it out of headings, lists, tables, blockquotes, code blocks, and raw HTML, and off any card side using reference-style link or image definitions; anywhere else it stays literal.
- Default to one short, recognizable root tag on every card. For a large deck, allow one coarse group tag in addition to the root; never exceed two tags per card or create a deeper public hierarchy by default. Use clear abbreviations, merge small topics into broader groups, and keep fine topics, difficulty, source-specific syllabus codes, and production statuses internal. Before drafting a large deck, state every public tag and the target card count for each group.

## Required generated cover

Every public catalog package must have a generated cover before its first publication; card images remain optional.

- Generate one original cover with an available image-generation tool.
- Open the first output at full size and at its smallest intended rendered size. Explicitly approve it unchanged only if its facts, visual appeal, composition, legibility, and crop safety are good enough to publish.
- If the first output is not good enough, record the reason, generate one replacement, and review it the same way. Make at most two cover-generation calls. If the second output is not publishable, stop before any catalog state change and report the blocker.

1. Read `AGENTS.md`, `apps/backend/src/catalog/authoring/`, `apps/backend/src/routes/catalog/admin.ts`, `apps/backend/src/routes/catalog/adminImageIngestion.ts`, and `apps/backend/src/routes/catalog/install.ts`, plus the sibling website's `src/lib/publicCatalogBuild.ts` and `.github/workflows/daily-vercel-rebuild.yml`. Use the current code as the API contract.
2. Before drafting, inspect active and recent deck-publication tasks; stop if another task is preparing the same subject or slug. On every run, web-search the current official Google Search documentation (`developers.google.com/search` and sources it links) on people-first content, generative-AI content, and spam policies. Use it, not SEO commentary, as the authority. Count a reviewed, installable package that makes material usable in this product as standalone value even when its facts or learning scope overlap another deck; do not reject it merely for that overlap. Stop only if the package or generated page exists mainly for search traffic and adds no such in-product learning value, or if it is a query-variant page without a distinct installable package. Before fixing the card schema, search the web for how learners actually query, study, and test the subject. Inspect at most three prominent same-subject decks or study tools. Compare coverage, recall directions, prompt and answer style, ordering, and extra facts; record which choices to keep or reject and why. Public access is not permission to copy or use material as LLM input: obey source terms, use protected guides, examinations, mark schemes, textbooks, and competitor decks only for lawful human comparison unless licensed, and draft common-knowledge content from compatible or independent sources. Prefer one retrieval target per card; use a composite prompt only when learners commonly practice it as one recall task. Enumerate useful mappings among the available facts: forward, reverse, and any additional or composite prompt. The product has no card-direction mode, so encode every supported direction as a separate card. Include a direction only when search evidence, common study practice, or clear retrieval value supports it; do not generate every permutation mechanically. Make each front the shortest unambiguous retrieval cue. Omit repeated question scaffolding when a visible deck or tag makes the expected response obvious; otherwise keep only the context needed to disambiguate bare words, symbols, numbers, images, or other cues on mixed-review, notification, export, and other standalone surfaces. Put the answer first on the back and keep reference context brief. Settle the deck subject, card source and order, author, stable slug, title, summary, Markdown description, language tags, license, content warning, and desired cover. Treat `languageTags` as audience languages. Include a language only when the package title, summary, description, prompts, answers, and required explanations are usable by that audience without translation; studying a language, script, or culture never qualifies by itself. Record one sentence in `review.md` justifying each language tag. Use a separate package when another audience needs materially different copy, prompts, explanations, or structure. Make the public text state exactly which fact mappings the cards practice, which plausible mappings were excluded and why, and how the sequence supports learning; verify those claims against the final cards. Create a separate slug only when distinct versions must remain independently installable. Keep each root tag distinct from other catalog subjects, add the shortest meaningful country, language, exam, or standard qualifier when needed, and avoid generic tags such as `study`, `cards`, or `deck`.
3. Prefer a Git-ignored `tmp/public-catalog/<slug>/` review bundle. Reuse the portable workspace package layout for `cards.json` and optional card files under `media/`; add `catalog.json` for catalog-only metadata, a required `cover.png`, `cover.jpg`, or `cover.webp`, and a generated `review.md` as the internal audit record. For a large deck, first add `plan.md` with the settled metadata, public tag counts, fine-grained internal coverage ledger, source, media, and license rules, and intended learning order. Draft and independently review topic-sized batches, then merge them into one master card set; treat card counts as estimates, not quotas. Only `cards.json` and referenced `media/**` entries belong in a workspace import ZIP; exclude the catalog-only, plan, and review files. Card images are optional. Before upload, manually open every final cover and unique card image individually at full size and at its smallest intended rendered size. Check factual correctness, clarity, centering, composition, spacing, legibility, visual consistency, and crop safety; fix every issue and record each image's pass in `review.md` together with its alt text, credit, and license. Contact sheets, hashes, dimensions, and metadata-only checks do not replace this review. Before choosing a cover aspect ratio, inspect the rendered catalog crops and the SEO metadata wiring. When one image must serve catalog and search or social previews, prefer a relevant, text-light, center-safe 16:9 image at least 1200 pixels wide and review every crop; do not assume the package cover feeds Open Graph, Twitter, or JSON-LD metadata.
4. Finalize public-only cards in the reviewed bundle. Use a source workspace and the agent API when the cards already belong in an account; upload its JPEG, PNG, or WebP card images through the workspace media endpoints and reference ready assets with `fcasset:` links. The workspace snapshot flow copies those images into the catalog version automatically.
5. Before any catalog state change, manually read every final card front and back from the actual deck data. Scripts may check mechanical properties such as count and order, but must not replace this content review. For strict-answer decks, compare every question and accepted answer directly with the authoritative source, including qualifiers, alternatives, caveats, and changing or location-dependent answers. For open-ended decks, judge each prompt and answer individually for correctness, relevance, clarity, internal consistency, and whether the answer makes sense and addresses the prompt; verify factual claims against authoritative sources when available. For a comprehensive course deck, reconcile the final cards with the internal coverage ledger, level boundary, and exclusions; fix gaps, accidental advanced-level leakage, and count-driven filler. Record and resolve every finding before publication. If the bundle contains media, a fresh independent reviewer must repeat the per-image review on every final file after the last image change; do not publish until every image passes.
6. Before the first catalog state change, hash the finalized bundle or record the finalized workspace card IDs and order, preselect replay-safe package and version IDs, and resolve public state by slug with `GET /v1/catalog/packages/{slug}` and draft state by the replay-safe package ID with `GET /v1/admin/catalog/packages/{packageId}`; stop if any finalized input changes. Never query the database or `/v1/admin/reports/query` for publication validation. If package creation returns a slug conflict, stop and report it; do not investigate through either forbidden query path. Load `FLASHCARDS_OPEN_SOURCE_API_KEY` from a local secrets file kept outside this repository; never print or commit it. Prefer the `/v1/admin/catalog` endpoints with `Authorization: ApiKey $FLASHCARDS_OPEN_SOURCE_API_KEY`; the key owner's profile email must have an active `auth.admin_users` grant. A signed-in browser session is only an optional alternative, must not be required while the API key succeeds, and requires CSRF protection for state-changing requests. Create or update the author and package draft. For a cover, append each non-null reviewed `altText`, `credit`, and `license` value to `URLSearchParams`, then upload the raw bytes with the image `Content-Type` to `PUT /v1/admin/catalog/packages/{packageId}/cover?${params.toString()}`; it normalizes and attaches the image as `cover`. Keep those reviewed values with the cover throughout publication; do not replace them with title or description fallbacks. For each direct card image, append the reviewed non-null `altText`, `credit`, and `license` values to `URLSearchParams`, then upload the raw bytes with the image `Content-Type` and `x-package-media-key` to `POST /v1/admin/catalog/packages/{packageId}/media-assets/images?${params.toString()}`. Keep those reviewed values unchanged across retries; the endpoint rejects metadata that conflicts with an existing package media key. Save every created author, package, media, and version ID in the review bundle.
7. Treat card order as a learning contract. Introduce prerequisites before dependent knowledge and progress from simple to complex inside each coherent topic; do not group all easy cards across unrelated topics before all difficult cards. Design one sequence across all directions, while leaving long-term spacing and interleaving to the review scheduler. Keep a fact's forward, reverse, and near-duplicate variants apart so one does not cue the next; target at least three unrelated cards between cards from the same internal concept group, separate confusingly similar items, and avoid predictable runs. Use a deterministic order and manually inspect the resulting distances. For a reviewed bundle, call `POST /v1/admin/catalog/packages/{packageId}/versions` with explicit unique ordinals `1..N`. For a workspace snapshot, pass `cardIds` to `POST /v1/admin/catalog/packages/{packageId}/versions/from-workspace` in the exact intended sequence. Move the immutable version through `draft -> submitted -> approved`, then publish it with the review-status and publish endpoints. After an ambiguous `5xx`, reload the existing package draft or public status and reuse known IDs and the same payload only when safe; never create replacement resources automatically. Treat a request to create, add, or publish a public catalog deck as authorization to make it public after the independent readiness checks pass; do not request separate approval. If the user explicitly asks for preparation or review only, stop before the first state-changing call. Corrections after publication require a new version.
8. Verify through bounded lookups, never through `GET /v1/catalog`, that every published package, version, card, tag, cover, and media field matches the finalized bundle. Read `GET /v1/catalog/packages/{slug}` for the package fields, the author, `coverPackageMediaKey`, and every entry of `mediaAssets`; it always resolves to the package's latest published version, so first confirm that its `latestVersion.packageVersionId` is the version you just published and stop if it is not, because every other field in that response then describes a different snapshot. Treat `mediaAssets` as a superset of this run's uploads, not a set you can partition by origin: every new version also receives a copy of the package's entire draft media set, including keys no card references and keys only an earlier version used, so an entry you did not upload is not by itself a defect and its origin is not decidable here. Require that each image you uploaded in step 6 appears under the `packageMediaKey` its upload response returned, with `mimeType` exactly `image/jpeg` because both upload endpoints re-encode every image whatever format was sent, and with `altText`, `credit`, and `license` equal to that same upload response, which reports them already trimmed; compare against it rather than against the strings you recorded locally. An empty value is never collapsed to `null`: the upload rejects it with `400 CATALOG_INVALID_INPUT`, so omit any parameter you have no reviewed value for. Of every other entry require only that its `mimeType` is one the public catalog delivers — `application/pdf`, `audio/mpeg`, `image/jpeg`, `image/png`, or `image/webp`. Require `sizeBytes` to be present and plausible on every entry, and never fail an entry merely because it differs from the local file's byte length. Read `GET /v1/catalog/package-versions/{packageVersionId}` for the exact published version, confirming its `packageVersionId`, `versionNumber`, `slug`, `title`, `summary`, `languageTags`, `cardCount`, `publishedAt`, and author; `versionNumber` and `publishedAt` are assigned by the server when the version is created and published, so check those two for presence and plausibility rather than against a reviewed value. Read `GET /v1/catalog/package-versions/{packageVersionId}/cards?limit=100` for card text, order, `cardType`, tags, and media keys; it returns at most the first 100 cards by ordinal and accepts no offset or cursor, so when `cardCount` exceeds 100, check the remaining ordinals against `https://d2bq3tvt7zf1kf.cloudfront.net/catalog/latest.json`, polled as in step 10 until it contains the `packageVersionId`. In that artifact the version's cards are the top-level `cards[]` entries whose `packageVersionId` matches, carrying `frontText`, `backText`, `ordinal`, `cardType`, `tags`, and `mediaAssetIds`; a card there names no media key, so resolve each `mediaAssetIds` value to its `packageMediaKey` through the top-level `mediaAssets[]` entry with the same `packageMediaAssetId`. The two transports do not expose the same media set, so never diff ordinals 1-100 against ordinals 101+: the endpoint returns each card's stored key list verbatim, while the artifact deduplicates that list and unions in every `fcasset:` id from the same card's `frontText` and `backText`. Compare the two as sets rather than by length: every endpoint key must appear in the artifact's set, which is legitimately larger for a bundle-created card whose text references a key the card did not list, and legitimately shorter for a card that lists the same key twice. Judge each card's media against the images that card is meant to show; on a reviewed bundle those are the keys you sent, while on a workspace snapshot the server assigns the package media keys itself and rewrites the card text to match, so there check that each key resolves to a `mediaAssets` entry of this version rather than to a string you recorded. Check every published field either way; never shrink the check to the cards one endpoint happens to return. Do not install the version into a verification workspace or verify install buttons, links, or actions.
9. Before rebuilding the website, inspect the sibling website for existing articles that are materially related to the published deck. For each materially relevant existing article, add a natural contextual internal link from every existing localization whose page locale matches an eligible audience-language tag to the deck's canonical `/catalog/packages/<slug>/` page, following the surrounding content and frontmatter conventions. Do not require links from localizations whose page locale matches none of those tags. Remove backlinks from localizations that become audience-ineligible after a package correction. Verify that the anchor text and nearby claims match the final deck. Do not add tangential links or create a new article solely to manufacture a backlink; if no relevant article exists, record that outcome and continue.
10. The website builds from the public catalog CDN artifact, which is rebuilt automatically about 15 seconds after publication, so before triggering the rebuild, poll `https://d2bq3tvt7zf1kf.cloudfront.net/catalog/latest.json` until its `packageVersions` contains the published `packageVersionId`; rebuilding earlier builds the site from a pre-publication artifact and fails the checks below for a reason that looks unrelated. That file is served with `Cache-Control: public, max-age=60` and every CloudFront edge honours that TTL independently, so a poll satisfied at your edge does not prove the builder's edge has stopped serving the pre-publication copy; wait a further 60 seconds after the gate passes before triggering the rebuild. If the artifact still lacks the version after five minutes, tell the two causes apart by the artifact's `generatedAt`. If `generatedAt` is still older than the publication, the rebuild trigger never landed: the backend fires it without awaiting it and swallows its own failure, so the artifact stays stale until the next admin write. Re-trigger it exactly once with `PUT /v1/admin/catalog/packages/{packageId}/draft` and poll five minutes more; that PUT replaces the whole draft rather than patching it, so resend every settled value unchanged — `authorId`, `slug`, `title`, `summary`, `description`, `languageTags`, `license`, `contentWarning`, and `coverPackageMediaKey` — because the request rejects a missing field outright, and the only alternative the parser accepts for `coverPackageMediaKey` is `null`, which clears the package cover that every later version inherits. Never re-trigger a second time: if the version is still absent when that second poll ends, re-read `generatedAt` and follow whichever branch it now indicates, and when it is still older than the publication, stop without rebuilding the website and report the published version, the stale `generatedAt`, and the failed re-trigger. Do not retry the publish call, which returns `409 CATALOG_PACKAGE_VERSION_NOT_APPROVED` once the version is published. If `generatedAt` has advanced past the publication and the version is still absent, the artifact re-checked public eligibility across the package, author, version, media, and cards and silently omitted this version. The publish call ran that identical check over the same inputs before flipping the status, and nothing rewrites a published version's own fields, media, or cards afterwards, so look first at the two records that check still reads and a later admin write can still change: the author record and the package `slug`. Repair whichever one is unsafe; publish a corrective new version only when the deck's own frozen data is at fault. Then rebuild the sibling static website through its existing deployment workflow, wait for the Vercel deployment itself to reach `Ready` rather than treating the deploy-hook workflow as completion, then make an unauthenticated request to `https://flashcards-open-source-app.com/catalog/packages/<slug>/` and require HTTP `200`. Treat this public production URL as the final delivery check; never use database or `/v1/admin/reports/query` queries to verify publication. Check the live HTML and Markdown pages, canonical URL, metadata and JSON-LD, sitemap entry, actual cover crops, media rendering, and any article links added in the previous step. After all checks pass, report the published result with its public links, package version ID, linked articles or the absence of a relevant article, and verification summary.
